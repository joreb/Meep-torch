# 2D TM driven FDFD — plan

Status: approved (user, 2026-08-17), implementing
Driver: steady-state / high-Q response without time-stepping (the SHG
buildup problem class), exact single-solve adjoints for inverse design,
and an independent frequency-domain cross-check on FDTD results.

## Design constraints

Purely additive: one new module `meep_torch/fdfd.py` + one test file.
No edits to existing solvers/ports/adjoint code. Reuses as-is:
eps rasterization + gdsfactory adapter, materials n(f) (evaluated
exactly at the solve frequency — no pole fitting), `Port`, `solve_1d`
mode profiles, `DesignRegion`/filters (they only paint eps).

## Method (ceviche-style)

Helmholtz on the node grid, natural units (c = eps0 = mu0 = 1):
`(1/sx d/dx (1/sx' d/dx) + 1/sy d/dy (1/sy' d/dy) + w^2 eps) Ez = -iw Jz`
with complex-stretch PML `s = 1 + i sigma/w`, cubic sigma ramp,
sigma_max from R0 = 1e-6 (matching the CPML parameterization). Sparse
assembly (scipy), direct LU (splu), Dirichlet outer boundary behind the
PML. ~seconds at our 2D sizes on CPU.

Differentiability: custom autograd Function. Forward caches the LU
factorization; backward is ONE adjoint solve with the transposed
factors (`trans='T'`) — no checkpointing, no step-count memory.
`dL/deps_j = -2 w^2 Re[lambda_j E_j]`, `lambda = A^{-T} conj(g)`;
the sign/factor is gated by a finite-difference test, not trusted.

S-parameters: mode-profile overlap on the Ez line + straight-guide
reference-run normalization (the established two-run pattern). NOT via
`decompose` — that expects the FDTD DFT (E, H) accumulator layout, and
synthesizing a frequency-domain Hy line means re-deriving the Phase-4
sign conventions for zero benefit.

## Gates (tests/examples/test_fdfd.py)

1. Straight waveguide: |S21|^2 = 1 within 2%.
2. Adjoint gradient vs central finite differences on a small grid,
   through a real |a|^2 objective: rel err < 1e-5.
3. Cross-solver: transmission of a scattering structure agrees with
   `run_tm` + `decompose` within a few % (discretization-level, not
   bit-level — different solver class).

## Phase 2 (user-requested follow-ons, after CPU gates pass)

- **GPU tier via torch-sla** (user-supplied; supersedes the cupy-splu
  idea — cupy factorizes on CPU and only solves on GPU, torch-sla is
  native torch with built-in adjoint autograd, Apache-2.0, and offers
  true GPU direct LU through its cuDSS backend): `backend="torch-sla"`
  opt-in behind a try-import, no hard dependency. Probed 2026-08-17:
  complex128 solve + autograd pass on CPU and CUDA (rel err 2e-16 /
  9e-11); at 240k complex unknowns GPU solve 0.28 s vs scipy LU
  factorization 13.9 s — BUT that probe matrix was diagonally dominant
  and cuDSS was absent, so torch-sla used a GPU Krylov fallback that
  the real INDEFINITE FDFD Helmholtz may defeat. Gate before adoption:
  match the scipy backend < 1e-8 on the actual FDFD parity structure;
  if Krylov stalls there, require the cuDSS extra for the GPU path.
- **Unified facade** `meep_torch/solvers.py`: `sparams(eps, dx, freq,
  ports, method="fdtd"|"fdfd")` wrapping the established FDTD chain
  (house pulse/T_RUN/axis_sign conventions baked in) and the FDFD
  module; differentiable via either engine; parity test asserting both
  agree on one structure.

## Out of scope

TE polarization, 3D, dispersive-material poles inside the solve
(evaluate eps(f) per solve instead), nonlinear FDFD (undepleted SHG =
two chained linear solves, built LATER on top, not inside the solver).
